## User Scenarios & Testing *(mandatory)*

### User Story 1 - 贡献者快速验证变更 (Priority: P1)

作为 Agent21 贡献者，我希望用一个明确、可重复的验证入口检查本次改动，
并在合并前获得针对核心逻辑、主要工作流和质量约束的明确结果，
从而在不理解全部适配器细节的情况下安全贡献代码。

**Why this priority**: 快速且可信的日常反馈是测试体系被持续使用的前提，
也是阻止低成本缺陷进入主分支的第一道门禁。

**Independent Test**: 在一个仅修改核心逻辑的示例变更上运行贡献者验证流程，
确认它能在限定时间内给出通过或包含失败位置、场景和修复线索的失败结果。

**Acceptance Scenarios**:

1. **Given** 一个满足质量要求的变更，**When** 贡献者执行标准验证，
   **Then** 核心逻辑和主要工作流检查全部通过，并返回成功状态。
2. **Given** 一个破坏配置校验或同步行为的变更，**When** 贡献者执行标准验证，
   **Then** 验证失败，并明确指出受影响的行为和复现场景。
3. **Given** 一个只修改文档且不影响行为的变更，**When** 贡献者执行标准验证，
   **Then** 系统运行与风险相称的最小检查，而不要求无关的完整发布验证。

---

### User Story 2 - 防止 Agent21 损坏用户项目 (Priority: P1)

作为维护者，我希望在隔离的代表性项目中验证初始化、同步、迁移、技能管理和 MCP 管理，
确保重复执行、无效输入、权限错误或中途失败不会静默覆盖用户文件、逃逸项目边界或留下不可恢复状态。

**Why this priority**: Agent21 会修改开发者项目；保护用户资产比单纯验证函数返回值更重要，
安全回归必须阻断合并和发布。

**Independent Test**: 在包含已有配置、未托管文件、只读文件和恶意路径的隔离项目集中
执行所有会写入文件的核心命令，比较执行前后状态并验证诊断和恢复能力。

**Acceptance Scenarios**:

1. **Given** 一个空项目，**When** 执行初始化，**Then** 只创建声明的托管资产，
   成功结果可由健康检查确认，重复执行不产生额外差异。
2. **Given** 一个同时包含权威配置和既有工具配置的项目，**When** 执行同步或迁移，
   **Then** 生成结果符合已声明契约，未托管内容保持不变或获得明确且可恢复的冲突处理。
3. **Given** 非法路径、无效配置、只读目标或执行中断，**When** 执行写入型命令，
   **Then** 命令可控失败，不写出项目边界、不泄露敏感信息，也不留下无法识别的半完成状态。

---

### User Story 3 - 维护适配器与生成文件契约 (Priority: P2)

作为适配器维护者，我希望每个已声明支持的 Agent 都有统一的最低兼容契约和稳定输出基线，
从而在调整模板、映射规则或共享配置时立即发现非预期差异。

**Why this priority**: 多 Agent 兼容是 Agent21 的核心价值；适配器输出漂移可能一次影响多个工具，
但这套验证可以在核心安全流程建立后独立扩展。

**Independent Test**: 选择任一已实现适配器，以相同的权威输入执行其验证，
确认能力分类、输出集合、稳定内容和不支持项均与兼容矩阵一致。

**Acceptance Scenarios**:

1. **Given** 一个声明为原生支持的 Agent，**When** 执行兼容验证，
   **Then** 系统确认它复用权威来源且没有产生冗余第二真源。
2. **Given** 一个需要映射或转换的 Agent，**When** 执行兼容验证，
   **Then** 生成文件集合和稳定内容与已批准基线一致。
3. **Given** 模板或适配规则产生未经批准的输出变化，**When** 执行回归验证，
   **Then** 验证失败并展示可审查的差异，而不是自动接受新基线。

---

### User Story 4 - 发布跨平台可信版本 (Priority: P2)

作为发布负责人，我希望发布候选版本在 Linux、macOS 和 Windows 上通过完整门禁，
并验证交付物可安装、公开命令可调用且核心工作流可完成，避免把平台差异或打包问题交给用户发现。

**Why this priority**: Agent21 面向跨平台开源团队，发布验证直接决定用户能否安全采用；
它依赖前述核心测试资产，因此优先级位于日常验证之后。

**Independent Test**: 对一个候选发布物执行三平台验证和全新环境安装检查，
确认任何测试、构建、安装或公开命令失败都会阻断发布。

**Acceptance Scenarios**:

1. **Given** 一个满足全部门禁的候选版本，**When** 执行发布验证，
   **Then** 三个平台均完成安装和核心命令验证，并产生可追踪的通过证据。
2. **Given** 任一平台出现路径、链接、权限、安装或 CLI 契约失败，
   **When** 执行发布验证，**Then** 发布被阻断并明确标识失败平台与场景。
3. **Given** 一个公开命令被删除、重命名或改变成功/失败语义，
   **When** 执行契约验证，**Then** 验证失败并将其标记为潜在不兼容变更。

### Edge Cases

- 空项目不存在任何 Agent21 或第三方 Agent 配置。
- 同一项目同时存在 `AGENTS.md`、`CLAUDE.md`、`.mcp.json` 和多个工具目录。
- 配置缺少必填字段、包含未知字段、格式损坏或引用不存在的路径。
- 同一状态变更命令连续执行两次或多次。
- 目标文件只读、目标目录无写权限，或执行过程中发生部分失败。
- 输入包含绝对路径、父目录跳转、非法 Skill 名称或指向项目外的链接。
- 平台不支持符号链接，或当前用户没有创建符号链接的权限。
- 生成结果包含时间、绝对路径或平台分隔符等环境相关内容。
- 已有托管产物发生漂移，或目标位置存在同名未托管文件。
- 第三方 Agent、远程 Skill 来源或 MCP 服务不可用。
- 发布物可以构建但无法安装，或安装后缺少公开命令入口。
- 测试进程并发运行时使用相同 fixture 名称，但不得互相污染状态。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 测试体系必须提供核心逻辑、真实工作流、完整 CLI 行为和跨平台兼容四个可独立执行的验证层级。
- **FR-002**: 贡献者必须能够通过单一、文档化的入口运行与日常变更相称的验证，并获得明确的成功或失败状态。
- **FR-003**: 所有会修改项目状态的测试必须在隔离项目中运行，不得读写贡献者的真实项目资产或依赖测试顺序。
- **FR-004**: 核心逻辑验证必须覆盖配置加载与校验、项目扫描、manifest、适配器、Skill 管理和 MCP 管理。
- **FR-005**: 工作流验证必须覆盖初始化、同步、配置迁移、Skill 生命周期、MCP 配置处理和健康检查的成功与失败路径。
- **FR-006**: 每个声明为 MVP 公共契约的 CLI 命令必须验证命令存在、主要参数可用、退出状态语义稳定且用户输出可诊断。
- **FR-007**: 每类稳定的生成文件必须具有可审查的内容基线；环境相关内容必须在比较前规范化，基线变化必须显式批准。
- **FR-008**: 每个会改变项目状态的核心命令必须验证幂等性；相同输入下重复执行不得产生新的文件差异、重复记录或额外副作用。
- **FR-009**: 测试体系必须验证未托管文件不被静默覆盖，并验证冲突、失败和中断后的状态可识别且可恢复。
- **FR-010**: 安全验证必须覆盖项目边界逃逸、非法 Skill 名称或路径、不可信来源输入、只读或无权限目标以及敏感信息输出。
- **FR-011**: Linux、macOS 和 Windows 必须验证核心 CLI 契约、项目路径、权限行为，以及链接不可用时声明的产品行为。
- **FR-012**: 每个已实现且声明支持的 Agent 适配器必须在兼容矩阵中标识为原生、兼容映射、转换或不支持，并至少具有一个可判定的契约验证。
- **FR-013**: 尚未实现或仅列入后续路线图的适配器不得成为 MVP 通过条件，但测试体系必须允许它们沿用相同契约结构加入。
- **FR-014**: 合并请求门禁必须覆盖基础质量、核心逻辑、主要工作流和覆盖率；任何强制项失败必须阻止合并。
- **FR-015**: 主分支门禁必须在合并请求门禁之外覆盖完整 CLI、生成文件回归和多平台兼容验证。
- **FR-016**: 发布门禁必须覆盖完整回归、交付物构建、全新环境安装和公开 CLI 冒烟验证；任一强制项失败必须阻止发布。
- **FR-017**: MVP 的整体自动化测试覆盖率不得低于 80%，配置、适配器、Skill 和 MCP 等核心区域不得低于 90%；任何排除项必须记录理由。
- **FR-018**: 默认日常验证不得要求真实第三方 Agent、远程 Skill 仓库或 MCP 服务在线；外部边界必须可在受控环境中验证。
- **FR-019**: 每个失败结果必须标识验证层级、命令或场景、预期与实际差异，并提供足以本地复现的线索，同时不得暴露凭证。
- **FR-020**: 行为变更和缺陷修复必须先增加能失败的测试或可执行验收检查，再实现修改并保留回归用例。
- **FR-021**: 测试文档必须说明本地验证、基线更新、跨平台失败排查和发布门禁的使用方式，使首次贡献者无需维护者口头指导即可开始。

### Configuration, Compatibility & Safety *(mandatory for Agent21 behavior changes)*

- **Authoritative Inputs**: 产品规格、项目宪章、公开 CLI 与配置契约、Agent 支持矩阵及经批准的稳定输出基线是测试判定依据；测试生成报告不得成为产品配置真源。
- **Managed Outputs**: 测试报告、覆盖率结果、临时项目、差异报告和候选发布验证记录均为可重建产物；稳定输出基线是受评审的版本化测试资产。
- **Affected Agents**: MVP 只强制验证已实现且声明支持的适配器；Claude、Codex、Cursor、OpenCode、Pi、WorkBuddy 和 Qoder 均可登记，但未实现项必须明确标记而非伪装通过。
- **Platforms / Sync Modes**: Linux、macOS、Windows 以及产品声明支持的 `auto`、`copy`、`symlink` 模式必须具有明确验证范围；平台能力不足时验证已声明的回退或失败行为。
- **Recovery & Drift**: 写入型场景必须验证幂等、漂移检测、未托管文件保护和失败恢复；任何基线变化必须展示差异并由评审显式接受。
- **Security Boundary**: 测试写入必须限制在隔离工作区；日志和测试证据不得包含真实凭证；测试夹具不得执行 Skill 内容或访问未声明的外部服务。

### Key Entities *(include if feature involves data)*

- **Project Fixture**: 表示一种隔离的用户项目状态，包含已有文件、Agent 配置、权限、损坏状态和预期保护边界。
- **Validation Case**: 描述前置状态、用户动作、预期结果、适用平台和所属验证层级。
- **Adapter Contract**: 描述某 Agent 的能力分类、权威输入、允许输出、不支持项和兼容判定。
- **Stable Output Baseline**: 表示确定性生成结果的已批准版本，以及需要忽略或规范化的环境差异。
- **Validation Run**: 记录触发阶段、执行范围、通过或失败状态、差异和可复现证据。
- **Release Gate**: 聚合发布所需的回归、平台、构建、安装和 CLI 验证状态，并决定是否允许继续发布。

### Scope Boundaries

**In Scope**:

- Agent21 MVP 核心命令与文件工作流的自动化验证。
- 核心逻辑、集成流程、CLI、稳定生成结果、幂等、安全和三平台兼容门禁。
- 面向合并请求、主分支和发布候选版本的分层质量门禁。
- 支持 Test First 与 AI 辅助开发的可复用验证结构和贡献者文档。

**Out of Scope**:

- 实现 Agent21 的业务命令、适配器或尚未交付的产品能力。
- 真实启动或控制 Claude、Codex、Cursor 等第三方 Agent 进行日常验证。
- 要求远程 Skill 仓库、MCP 服务或包注册表在默认测试中在线。
- 建设完整性能压测、远程注册表测试或第三方服务可用性监控体系。
- 自动接受生成文件基线变化，或替代维护者对兼容性变更的评审。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的 MVP 公共 CLI 命令至少具有一个成功路径和一个可诊断失败路径的自动化验证。
- **SC-002**: 至少 90% 的常规贡献变更能在 10 分钟内获得明确的合并请求门禁结果。
- **SC-003**: 100% 的写入型核心命令均通过重复执行一致性、项目边界保护和未托管文件保护验证。
- **SC-004**: 所有声明支持的适配器均在兼容矩阵中有明确状态，且 100% 已实现适配器至少通过一个契约验证。
- **SC-005**: 每个发布候选版本均在 Linux、macOS 和 Windows 上通过核心兼容验证，且完成一次全新环境安装和公开命令冒烟检查。
- **SC-006**: MVP 整体自动化测试覆盖率达到 80% 以上，配置、适配器、Skill 和 MCP 核心区域达到 90% 以上。
- **SC-007**: 至少 90% 的首次贡献者能够仅依据仓库文档在 15 分钟内启动标准验证，无需维护者口头协助。
- **SC-008**: 同一候选版本连续执行 20 次标准验证，不出现无法由代码或环境变更解释的间歇性失败。
- **SC-009**: 对预置的配置损坏、权限、路径越界、输出漂移和安装失败场景，100% 能阻断相应门禁并给出可复现线索。

## Assumptions

- Agent21 是面向开发团队的本地 CLI，会读取和修改当前项目中的 Agent 配置与托管产物。
- MVP 公共能力以产品规格中已交付的 `init`、`sync`、`doctor`、Skill 管理和 MCP 管理为准；测试规格不提前承诺未实现命令。
- Linux、macOS 和 Windows 的受控验证环境在主分支与发布阶段可用。
- 第三方 Agent 和外部服务的最低契约可以通过受控替身或固定输入输出验证；真实互操作验证可作为独立的非阻塞扩展。
- 稳定输出基线只覆盖用户可见且确定性的内容，时间、绝对路径和平台差异在比较前会被规范化。
- 已有用户文件的具体冲突策略由对应产品契约决定，但任何策略都不得静默丢失内容，且必须可诊断、可恢复。
- 配置迁移的字段级规则和每个适配器的完整输出格式将在对应产品规格或规划阶段定义；本功能负责验证已批准契约，而不自行发明契约。
- 合并请求门禁优先快速反馈；较慢的完整 CLI、多平台、安装和发布验证由主分支或发布门禁承担。
